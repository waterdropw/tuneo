# Tuneo 儿童多模态陪伴

基于阿里云 Qwen-Omni-Realtime 全模态大模型的儿童实时语音陪伴功能。孩子说话，AI 用温暖、符合年龄的语音实时回应。识物、讲故事、陪伴对话、涂鸦理解等场景都由同一套自然对话覆盖。

> 当前手机端 App 为 MVP 验证版；视频流（摄像头取帧）已实现（自动抓帧：5s 一帧 / 1s 一帧）。

## 产品形态

**最终产品形态**是一个**无显示屏**的小盒子（约半个手机大小），孩子挂在脖子上、垂到胸前位置。硬件仅包含：

- **麦克风**：拾取孩子的声音
- **喇叭**：播放 AI 的语音回应
- **摄像头**：拍摄孩子前方第一视角画面（识物 / 绘本 / 安全提醒）

> 无屏意味着交互完全靠语音 + 摄像头；家长侧配置与数据查看需另配手机 App 或微信小程序（待规划）。当前手机端 App 只用于功能验证。

## 核心特性

- **全程实时连续**：服务端 VAD 自动检测说话开始/结束，无需按钮，随时能聊
- **全模态**：一个模型同时处理语音输入与语音输出（文字字幕同步）
- **年龄段可切换**：幼儿 / 儿童 / 自适应，切换人格与语言难度
- **儿童内容安全**：系统提示词约束 + 服务端内容审核兜底

## 应用场景

### 当前可用（仅语音）

| 场景 | 孩子做什么 | AI 回应 |
|------|-----------|---------|
| 陪伴对话 / 闲聊 | 自由说话 | 温柔、鼓励式语音回应 |
| 讲故事 | 「讲个小恐龙的故事」 | 语音编讲儿童故事 |
| 问答 / 知识科普 | 「为什么天是蓝的？」 | 用年龄匹配的语言解释 |
| 语言类互动（儿歌 / 绕口令 / 猜谜） | 提出要求 | 语音配合 |

### 需视频通道（预留，未实现）

| 场景 | 依赖 | 说明 |
|------|------|------|
| 识物认知学习 | 摄像头取帧 | 对准物体，AI 认出并告诉孩子「这是苹果」，可双语 |
| 看图讲故事 / 绘本讲解 | 摄像头 / 照片 | 拍绘本画面，AI 看图用儿童口吻讲解 |
| 涂鸦 / 绘画理解 | 摄像头取帧 | 孩子画画，AI 识别并鼓励、描述、延伸 |

## 年龄段模式

| 模式 | 目标年龄 | 特点 |
|------|---------|------|
| 幼儿 | 2–6 岁 | 短句、重复、鼓励、语气亲切活泼 |
| 儿童 | 6–12 岁 | 语言更丰富，可讲故事、科普 |
| 自适应 | 自动 | 根据孩子语言水平自动调整用词 |

## 技术架构

- 模型：`qwen3-omni-flash-realtime`（默认，可配置）
- 端点：`wss://dashscope.aliyuncs.com/api-ws/v1/realtime`
- 输入：PCM 16kHz 单声道 16-bit 音频（复用现有 `microphone-stream` 模块）
- 输出：PCM 24kHz 单声道 16-bit 音频 + 文本
- 交互：`session.update` / `input_audio_buffer.append` / `response.cancel`，服务端 VAD 模式

### 关键文件

| 文件 | 职责 |
|------|------|
| `src/services/OmniRealtimeService.ts` | 实时多模态对话服务（WebSocket 协议） |
| `src/services/OmniAudioPlayer.ts` | 累积 PCM → WAV → 播放 |
| `src/services/audioCodec.ts` | PCM / base64 / WAV 编解码工具 |
| `src/stores/companionStore.ts` | 年龄段 / 音色 / 系统提示词 |
| `src/navigation/screens/Companion.tsx` | 陪伴屏幕 |

## 快速开始

1. 配置 API Key（环境变量）：

   ```
   EXPO_PUBLIC_DASHSCOPE_API_KEY=sk-xxx
   ```

2. 启动 dev client 并导航到「儿童陪伴」屏幕：

   ```bash
   npm run ios      # 或 npm run android
   ```

3. 点「开始陪伴」，说话即可。

## 产品设计提升空间（持续补充）

> 从产品设计师视角梳理的改进方向，随产品演进持续更新。当前为手机端 MVP，最终形态为无屏挂脖小盒子，交互与信息架构需围绕「无屏 + 胸前第一视角」重新设计。

### P0 — 上架 / 信任前提

- **儿童隐私与合规**：麦克风 + 摄像头 + 云端大模型 + 每日对话落盘，涉及 COPPA / GDPR-K / 国内《儿童个人信息网络保护规定》。需先有「家长授权 + 数据留存策略 + 服务端代理」的完整方案。
- **API Key 服务端化**：`EXPO_PUBLIC_DASHSCOPE_API_KEY` 当前打进客户端包（见 README「已知限制」），正式发布必须走服务端代理。
- **安全提醒从 prompt 软约束 → 确定性检测**：当前「危险警示」写在 `prompts.json` 的 system prompt 里，依赖 LLM 视觉判断，存在漏检/误检/时延风险。需引入确定性 CV 检测（台阶/道路/尖锐物）+ 分级响应 + 家长告警通道。

### P1 — 核心体验

- **无屏的「听/想/说」状态表达**：无显示屏意味着「正在听 / 正在想 / 正在说 / 安全告警」需靠声音、指示灯、震动或肢体化语音表达，替代手机端的文字气泡与状态小字。
- **角色 / 情感存在感**：陪伴类产品的灵魂。手机上可用 Avatar（当前 `Avatar` 屏幕未与陪伴主流程打通）；无屏硬件上需一个可被孩子认同的角色人格（名字、语气、口头禅）。
- **家长端（手机 App 或微信小程序，待规划）**：付费者/决策者是家长。需要「今日摘要、安全事件记录、内容安全透明度、使用时长控制」。
- **幼儿主动破冰**：`prompts.json` 默认「其他时候保持安静」，但 2–6 岁孩子不会主动发起对话，沉默会被当成「坏了」。需低频温柔的主动引导。

### P2 — 交互与生命周期

- **自动识物替代手动按钮**：已移除「看这个」按钮，识物改为自动定时抓帧（5s/1s）。挂脖胸前第一视角下，仍可进一步做指向手势检测触发。
- **配置分层**：家长设置（年龄/音色/安全偏好）与孩子使用区分开。家长设一次后隐藏，孩子只面对角色。
- **生命周期管理**：退后台自动暂停、空闲超时、音量/免打扰、掉电处理。

### P3 — 打磨

- 移除调试 UI：`Companion.tsx` 中的 Prompt 编辑区、`音频 N 块 · 图片 N 帧` 统计。
- 音色人格化命名：`Tina / Cherry` 等 API ID → 「温柔姐姐 / 活泼哥哥」等家长可理解的人格描述。

## 成熟商用产品短板（TODO）

> 从「能否作为成熟商用产品上市」角度梳理的短板，按致命程度分三层：上市硬门槛 / 可靠性 / 体验与规模化。**标记 TODO，尚未实现。**

### TODO 一、上市硬门槛（当前一个都没满足）

- [ ] **安全提醒从「概率」变「确定」**：核心卖点之一是「胸前第一视角看到危险就提醒」，但现在危险判断写在 `prompts.json` 的 system prompt 里，靠 LLM 视觉输出，存在漏检/误检/时延不可控。商用上无法给出「99% 危险必提醒」的确定性 SLA，法务/保险过不去。需确定性 CV 检测 + LLM 只做语义兜底 + 家长告警通道。
  - 危险检测的完整链条：① 检测「有东西在动」→ ② 识别「是汽车/电动车/人」→ ③ 定位「在马路上？朝哪去？是否逼近」→ ④ 判断「危险吗」→ ⑤ 响应提醒。**光流只覆盖第①环**（运动检测），且帧间差分即可粗略替代，**不是危险检测的答案**。
  - 真正的技术路径：**目标检测模型**（识别汽车/电动车/人，如 YOLO 等）+ **深度估计**（判断距离/是否逼近）+ **真视频流 + 原生推理**（Vision framework 或移动端检测模型）。三者结合才能把「检测到快速移动物体」升级为「判断危险」。
  - 硬约束：检测高速物体需要高帧率视频流（15–30fps），当前 `expo-camera` 只能 1s 拍照，既无视频流、无像素访问、无原生计算——三样都缺。这是独立于「自适应帧率」的另一个量级工程。
  - **端侧检测现成方案调研（2026）**：需先换 VisionCamera v5（frame processor 拿真视频流），再叠加端侧推理库。目标检测：ExecuTorch `useObjectDetection`（YOLO/RF-DETR，COCO 80 类含 car/person/motorcycle/bicycle 等交通类）或 `vision-camera-plugin-object-detector`（ML Kit，粗分类）；场景分类：ExecuTorch `useClassification`（CLIP/EfficientNet）。硬前提：VisionCamera v5 是 2026 年 4 月 Nitro 架构重写，需 RN New Arch + prebuild（非 Expo Go）+ nitro-modules/worklets 等 peer 依赖；且检测只给出「有什么物体在哪」，距离/是否逼近/是否危险仍需深度估计或轨迹判断；功耗（15-30fps 端侧推理）仍是挂脖硬件的实打实约束。
- [ ] **儿童数据合规**：API Key 打进客户端包（`EXPO_PUBLIC_DASHSCOPE_API_KEY`），任何反编译者都能白嫖额度；每日对话落盘本地，但无家长授权体系、无数据留存策略、无删除权，撞 COPPA / GDPR-K / 国内《儿童个人信息网络保护规定》；儿童声纹长期上传云端属最敏感一类。
- [ ] **服务端缺失**：当前客户端直连阿里云百炼，无自有服务端做 API Key 托管、内容安全二次审核、用量计费、设备鉴权、家长端数据同步。这一步是「demo → 产品」的分水岭。

### TODO 二、可靠性（商用及格线）

- [ ] **断线自动重连**：当前断线后需手动重新开始。挂脖无屏设备上，断线 = 产品失效直到家长介入。需静默重连 + 断线期间本地降级。
- [ ] **语音链路 DSP**：无回声消除（AEC）、无降噪、无自动增益。真实环境（户外/电视背景/车内）拾音质量未知；端侧 VAD 在嘈杂环境下能否区分「孩子说话」vs「电视人声」未验证，直接决定计费是否失控。
- [ ] **质量保障体系**：无测试运行器、无 CI、原生 VAD 代码未真机编译验证。无回归保障，改 prompt/VAD 参数只能手动试。

### TODO 三、体验与规模化（决定能不能卖得动）

- [ ] **无屏状态表达**：孩子挂黑盒子，怎么知道「在听/没电/断网」？需灯光/震动/提示音构成的状态语言，且低功耗。
- [ ] **自动唤醒 / 开启陪伴**：当前需手动点「开始陪伴」按钮才建会话，VAD 只门控「已开启会话里的音频发送 + 打断」。无屏挂脖设备孩子不会按按钮，需「开机待命 → 检测到人声自动开启」；需解决待命态连接如何建（轻量连接 vs 完整会话）、误唤醒（电视/环境声误触发）、省电与计费（待命态是否推流）三个子问题。
- [ ] **绘本翻页时序**：prompt 已加「讲完当前页提示翻页」，但视频流 1s 才抓一帧，孩子快速翻页时模型可能跟不上（在旧页继续讲、或提示翻页时已翻过去）。需验证翻页后模型是否及时切换新页内容；若跟不上，需回到「视频帧率 / 按需抓帧触发」上解决，而非继续调 prompt。
- [ ] **视频帧率策略（主场景：自由行走 + 危险预警）**：产品主场景是孩子**自由行走不说话**时的持续危险预警，因此画面必须**固定节奏持续推帧**（不能靠「语音事件触发抓帧」——孩子不说话时危险预警会失效）。音画对齐（识物场景）是次要诉求，见下条。当前「固定节奏取最新帧」是架构内的低成本优化，只提升画面新鲜度，**不解决危险预警的可靠性**——危险预警真正瓶颈是「谁判断危险」（当前靠云端 LLM 提示词，有延迟/漏检/不可靠），需走确定性 CV 检测（见 TODO 一），那要求换库拿真视频流 + 本地推理，与当前拍照架构不兼容。
- [ ] **音画对齐（识物场景，次要）**：音频与图像两条独立通道时间不对齐——孩子指着苹果问「这是什么」时，图像 buffer 里可能是几秒前的旧帧。已排除：① timestamp——协议 append 消息无此字段，且模型多模态对齐是内部能力、不读客户端时间戳；② 高频抓帧缓冲区——`expo-camera` 拍照做不到高频，且高频抓帧功耗是挂脖硬件硬约束。方向待定：发送时刻跟随语音事件（`onSpeechStart`/`onSpeechEnd` 取最新帧补发），需权衡功耗与计费。
- [ ] **计费成本实测**：plus 模型 + 多模态的真实单用户成本、上下文累积长期成本曲线无实测数据，商用定价无法估算。
- [ ] **家长端商业闭环**：付费者是家长不是孩子。无家长端（今日摘要/安全记录/内容透明度），产品只有「孩子喜欢」一个维度，家长无法建立信任、不会续费。
